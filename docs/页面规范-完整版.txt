一、页面原则
1. 不得擅自改变页面布局。
2. 每次更新前后，都要与 2026-08-28 历史页面逐项对齐：
   - 模块顺序
   - 卡片结构
   - 折叠方式
   - 字体、颜色、间距
   - 业务选择下拉框
3. 只更新数据和分析内容，不随意改版。
4. 固定模块顺序：
   - 热点等级与热度值排行榜
   - 事件详情
   - 用户层面玩梗热点
   - 本地生活业务建议
   - 各平台热榜预览
5. “热度走势图”整栏删除，不在事件卡中保留入口、空状态或替代图表。
6. 页面不能出现乱码、问号替代文字或编码错误。
7. 每次生成后必须检查真实浏览器页面，不能只检查数据文件。
二、数据来源
1. 全网热点 TOP10
   - 固定来源：知微事见首页全网事件榜。
   - 用于全网事件观察和交叉验证。
2. 微博热点
   - 固定来源：微博官方热搜榜。
   - 保留排名、公开热度、抓取时间和链接。
3. 抖音热点
   - 固定来源：抖音官方热榜。
   - 保留排名、公开热度、抓取时间和链接。
4. 小红书趋势
   - 通过小红书“问点点”获得。
   - 上午提问：“昨天在小红书站内大家都在搜什么、讨论什么？”
   - 下午提问：“今天在小红书站内大家都在搜什么、讨论什么？”
   - 无法接入或没有结果时，要明确标注暂缺，不能沿用旧内容。
5. 不得擅自更换或混用未经确认的数据源。
6. 详细展开的核心热点必须进入微博或抖音官方榜单 TOP10。
7. 微博和抖音都要纳入考虑，不能只选抖音。
8. 核心热点不超过 4 个，不为了凑数强行补足。
三、核心热点选择
热点必须同时满足：
- 位于微博或抖音 TOP10。
- 具备一定破圈传播能力。
- 能与京东本地生活业务形成真实结合。
- 适合商业借势。
- 不属于高风险或冒犯性事件。
排除或谨慎处理：
- 灾害、事故、伤亡
- 违法犯罪
- 政治敏感事件
- 明星婚恋、家庭隐私
- 品牌危机、维权舆情
- 只有围观价值的普通新闻
- 无法与本地生活业务形成实际动作的话题
四、事件详情
事件卡只保留：
1. 等级、事件名称、话题、分数
2. 平台表现
3. 事件解释
4. 为什么热度高
5. 风险提醒
不得放入：
- 玩梗的可复刻模板
- 玩梗入选理由
- 独立的本地生活业务建议
- 热度走势图
“为什么热度高”的要求
必须针对每个事件独立分析，不能统一写成：
- “因为进入热搜榜”
- “讨论度高”
- “网友关注度高”
- “传播范围广”
应具体分析：
- 事件本身的冲突、反差或情绪价值
- 为什么用户愿意讨论
- 是否存在时间节点
- 是否与大众日常生活相关
- 是否具备视觉传播、身份代入或观点争议
- 不同平台的传播动力是否不同
五、用户层面玩梗热点
这是一个独立模块，不能与事件详情重复。
处理流程：
当天全部热榜 → 聚类成事件 → 查找参与信号 → 判断具体玩法 → 与事件详情查重 → 输出 meme-topics.json
候选标准
至少满足一项：
- 有可替换句式
- 有明确动作、舞蹈、模仿、变装或接力
- 有统一画面或拍摄结构
- 有固定音频、台词或问答格式
- 用户可以加入自己的经历继续创作
- 不理解完整背景也能参与
加分信号：
- 标题含“挑战、当我、原来、没想到、谁懂、××的样子”
- 同一句式出现多个变体
- 抖音存在动作或音乐型玩法
- 微博出现用户造句、改写和接龙
- 多平台出现相似表达
- 下午排名比上午明显上升
不应进入
- 普通新闻标题
- 比赛结果本身
- 明星私生活
- 灾害、事故、犯罪和伤亡
- 纯影视宣传
- 只有围观、没有复刻结构的话题
- 品牌参与容易显得冒犯的事件
内容级核验
对于抖音候选，应：
1. 找到对应热榜词的搜索结果页。
2. 查看前 10～20 条非官方用户视频。
3. 区分普通用户、媒体、明星、机构和品牌内容。
4. 提取重复出现的台词、动作、音频和拍摄结构。
5. 查看评论区是否出现接梗、模仿、求模板、求教程。
6. 至少发现 3 个独立普通用户采用相似模板，才能确认已经形成用户玩法。
7. 没有足够样本时，不能写“持续爆火”“全网都在玩”。
模型必须回答
1. 用户到底在玩什么？
2. 是否有清晰的复刻模板？
3. 普通用户能否在一分钟内理解？
4. 用户能否加入自己的内容？
5. 是否与事件详情重复？
6. 是否存在冒犯、版权、肖像或品牌安全风险？
页面表达
该板块是供本地生活业务借鉴和借势的入选内容，卡片使用：
- 平台 TOP几 · 热度多少
- 可复刻模板
- 入选理由
不能使用让普通读者困惑的技术表达，例如：
- 候选玩法模板
- 待核验
- verification unavailable
- observation only
但后台结构化数据仍应如实保留证据数量和核验状态，不能虚构用户样本。
六、本地生活业务建议
业务建议必须结合当天热点，并针对不同业务分别生成，不能只替换业务名称。
覆盖业务：
- 京东外卖
- 京东秒送
- 京东家政
- 七鲜小厨
- 七鲜咖啡
- 京东点评／京东真榜
- 京东旅行
- 七鲜美食MALL
每项建议都要回答：
1. 热点与该业务的真实连接点是什么？
2. 用户现在有什么具体需求或情绪？
3. 业务能提供什么真实供给？
4. 可以执行什么动作？
5. 如何形成传播证据？
6. 风险和边界是什么？
建议必须：
- 符合业务真实能力
- 有具体执行动作
- 有用户价值
- 有传播价值
- 能沉淀业务认知
- 避免空泛口号
- 避免所有业务使用同一个创意
- 不为了追热点强行关联
七、AI 分析要求
以下内容需要使用模型能力逐条生成，而不是只靠关键词模板：
- 事件解释
- 为什么热
- 入选理由
- 本地生活结合
- 风险边界
- 玩梗玩法分析
- 各业务针对性建议
模型输入至少包含：
- 标题
- 平台
- 排名
- 热度
- 抓取时间
- 证据链接
- 事件背景
- 风险信息
- 京东本地生活业务能力
没有执行 AI 分析时，不能用统一模板冒充深度分析。
八、历史页面
1. 每天生成的新页面作为当天首页。
2. 第二天更新时，将前一天完整页面保存到历史目录。
3. 历史页面必须保留当天最终版本，包括：
   - 平台榜单
   - 核心事件
   - 为什么热
   - 用户玩梗
   - 本地生活业务建议
4. 历史日期选择器要能够打开对应页面。
5. 更新今天的数据不能覆盖昨天的历史记录。
九、自动化
每日流程应为：
归档昨日页面 → 抓取固定来源 → 聚类预筛 → AI核心分析 → AI业务建议 → 玩梗内容核验 → 生成JSON与页面 → 布局校验 → 浏览器预览 → 用户确认 → 部署
自动绑定脚本只能更新：
- 日期
- 生成时间
- 等级文字
- 排行榜数据
- 平台榜单数据
不能自动覆盖：
- 人工或 AI 审核后的事件分析
- 用户玩梗文案
- 各业务建议
- 已确认的页面布局
十、发布要求
1. 用户要求先预览时，不得直接部署。
2. 用户确认后才发布到线上。
3. 发布后必须检查：
   - 线上 HTTP 状态
   - 页面日期
   - 核心热点数量
   - 标题、排名和热度
   - 玩梗板块
   - 业务建议
   - 历史页面链接
   - 是否存在乱码或旧缓存
4. 不能只看到命令成功就说已经部署。
